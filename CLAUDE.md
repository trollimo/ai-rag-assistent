# Корпоративный AI-ассистент по стандартам разработки

## Что строим

Внутренний ассистент поверх корпоративных стандартов разработки. UI: слева чат с ботом,
справа — «презентационная» панель ответа (текст/шаги/код/картинки/диаграммы), в стиле
слайда, а не голых чат-пузырей. Источник знаний — Markdown-инструкции + примеры кода,
источник истины — **Bitbucket** (без отдельной БД знаний; векторная база — производный,
пересобираемый индекс).

Ключевая идея: сократить путь «нашёл инструкцию → написал код руками» — за счёт кнопки
«Реализовать», которая делегирует задачу code-агенту (OpenCode) на рабочую папку
разработчика.

## Базовый репозиторий (не переписываем с нуля, расширяем)

Текущий код — это форк/развитие шаблона `trollimo/ai-rag-assistent` (Apache 2.0):

```
ai-rag-assistent/
├── rag-generation/        # Python: ingest .md → chunking → ChromaDB
│   ├── config/rag-sources.yaml
│   └── src/                # ingest + chunking + эмбеддинги
├── assistant-container/   # Docker: Web UI (Next.js/TS) + FastAPI + llama.cpp + MCP-сервер
│   ├── Dockerfile / Dockerfile.offline
│   ├── docker-compose.yml
│   └── MIGRATE_TO_LLAMASERVER.md   # план миграции Ollama → llama.cpp — ПРОВЕРИТЬ СТАТУС
```

Уже есть и работает: MD → ChromaDB пайплайн, Docker-упаковка веб+бэк, MCP-эндпоинт
(порт 9081, Streamable HTTP/SSE) под OpenCode.

Чего нет и предстоит дописать (см. ниже) — коннектор к Bitbucket, слой реакций/статистики,
авто-создание ветки+PR, рендер диаграмм, вызов OpenCode из UI.

## Целевые модули (в порядке вероятного приоритета)

1. **Bitbucket-коннектор** — вместо (или вместе с) сканом локальных `.md` в
   `rag-generation`: тянуть файлы из репозиториев через Bitbucket REST API, реиндексация
   по расписанию или по вебхуку `repo:push`. Уточнить: **Bitbucket Server (self-hosted) или
   Bitbucket Cloud** — у них разные REST API и авторизация сервисного аккаунта.
2. **Слой реакций/статистики** — лёгкая отдельная таблица (SQLite/Postgres, НЕ база знаний):
   `message_id, question, answer, source_doc, reaction ('попал'/'не попал'), timestamp`.
   Дашборд самых частых промахов.
3. **Авто branch + PR при пробеле** — по кнопке «оставить запрос на инструкцию» или при
   негативной реакции: через Bitbucket REST API создать ветку `new-instruction/<slug>`,
   закоммитить файл-заготовку (вопрос + тема + что нашлось частично), открыть PR в main.
   **Не мержить автоматически** — ждёт правки эксперта.
4. **Диаграммы в презентационной панели** — модель отдаёт Mermaid-разметку для сложной
   логики, рендер на фронте через mermaid.js. Не отдельный сервис — ещё один блок ответа.
5. **Кнопка «Реализовать» → OpenCode** — делегирование задачи локальному OpenCode
   (desktop app / CLI) на рабочую папку разработчика. Важно: **на Windows-машинах
   разработчиков Docker недоступен** — поэтому используем нативный OpenCode
   (MSI-инсталлятор, без Docker), не контейнер.
6. **MCP наружу** — оставить как в шаблоне, расширить источник данных на Bitbucket (п.1),
   желательно добавить цитирование источника (файл/ветка).
7. **Chroma в режиме сервера** — сейчас `rag-offline` (ассистент) и генератор
   индексации оба используют `chromadb.PersistentClient` напрямую на файл
   SQLite, и не умеют работать с базой одновременно (запись из генератора
   при запущенном ассистенте — конфликт блокировок, наблюдалось на практике).
   Актуально, когда переиндексация станет регулярной (п.1, вебхук
   `repo:push`) — нужен третий контейнер `chroma run` + оба клиента на
   `HttpClient` вместо `PersistentClient`, чтобы генерация не требовала
   остановки ассистента. Пока обходной путь — blue-green: генерировать в
   отдельную папку, подменять и рестартовать ассистента.

## Диагностика медленной индексации ChromaDB — решено (2026-08-21)

600 чанков по 1200 символов → ~15 минут на CPU без AVX512-VNNI (AMD Ryzen 5
3550H). Проверенные гипотезы:
- ~~эмбеддинги через Ollama~~ — Ollama в коде не используется вообще (уже
  удалена, `MIGRATE_TO_LLAMASERVER.md` был устаревшим и удалён).
- ~~не батчатся~~ — батчатся (`batch_size=256`), один вызов на весь корпус.
- ~~не хватает потоков~~ — ONNXRuntime уже грузит все ядра по умолчанию
  (750-830% CPU на 6-8-поточном CPU).
- ~~нужна модель полегче~~ — проверено предметно: `paraphrase-multilingual-
  MiniLM-L12-v2` даёт hit@1 2/6 против 18/20 у текущей модели на кириллице
  (путает несвязанные темы) — не годится. int8-квантизация той же
  `multilingual-e5-large` даёт всего +15% скорости (не 2.7-3.4x, как в общих
  бенчмарках — эффект требует AVX512-VNNI, которого нет на тестовом CPU) при
  просадке качества (MRR 0.929→0.882). Подробности и цифры —
  `rag-generation/docs/embedding-model-research.md`.

**Реальная причина**: 99% времени — чистый инференс `multilingual-e5-large`
(2.24 GB fp32, самая тяжёлая модель в каталоге fastembed), не запись в Chroma
(<1% времени). Это ожидаемо для такого класса модели на CPU без VNNI.

**Решение — не смена модели, а инкрементальная индексация** (реализовано в
`rag-generation/src/ingest.py`): хеш каждого чанка в `manifest.json`,
переэмбеддится только изменённое/новое, при смене
модели/чанкинга/embed-настроек — автоматический полный ребилд (fingerprint-
проверка). Правка одного файла в 630-чанковом корпусе → 1 чанк, секунды
вместо 15 минут.

Опционально (выключено по умолчанию, `RAG_EMBED_E5_PREFIXES=1`): префиксы
`query:`/`passage:`, которых требует e5, а `fastembed` не добавляет сам —
на текущем маленьком корпусе (20 запросов) дали небольшое ухудшение, не
улучшение. Стоит перепроверить, когда база вырастет.

вопросы, дальше — план по файлам и реализация.
