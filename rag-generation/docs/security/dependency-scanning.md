# Проверка зависимостей на уязвимости (SCA)

## Зачем
Большая часть кода в современном приложении — не написанный вами код, а
транзитивные зависимости. Уязвимость в них — такая же уязвимость в вашем
продукте, просто найденная не вами.

## Инструменты по языкам
- **Python**: `pip-audit` (использует базу PyPA/OSV), `safety`;
  ```bash
  pip-audit -r requirements.txt
  ```
- **Node.js**: `npm audit` встроен, для CI — `npm audit --audit-level=high`;
- **Java**: OWASP Dependency-Check (плагин Maven/Gradle), Snyk;
- **Go**: `govulncheck` (официальный от команды Go);
- **Универсально**: Trivy умеет сканировать и файлы зависимостей, и
  готовые Docker-образы одной командой.

## Куда встраивать
В CI — отдельный шаг, падающий на уязвимостях уровня `high`/`critical`,
но не блокирующий на `low`/`medium` (иначе пайплайн будет постоянно красным
из-за неисправимых на моменте уязвимостей в транзитивных пакетах).
```yaml
# пример шага в CI
- name: Dependency scan
  run: pip-audit -r requirements.txt --strict --fail-on-vulnerability-found
```

## SBOM (Software Bill of Materials)
Полный список всех зависимостей (включая транзитивные) с версиями —
генерируется автоматически (`syft`, `cyclonedx`), нужен для:
- быстрого ответа на вопрос «используем ли мы уязвимую библиотеку X» при
  появлении новой громкой CVE (как Log4Shell), без ручного поиска по всем
  репозиториям;
- части многих корпоративных compliance-требований.

## Практика: как реагировать на найденную CVE
1. Проверить, реально ли уязвимый код пути достижим в вашем сценарии
   использования библиотеки (не каждая CVE в зависимости эксплуатируема
   именно в вашем контексте использования).
2. Если да — обновить версию; если фикса ещё нет — искать обходной путь
   (отключить уязвимую фичу, добавить санитизацию на своей стороне).
3. Зафиксировать решение (даже «риск принят, фикса нет») — не оставлять
   молча без реакции, security-скан в CI будет продолжать падать иначе.

## Частая ошибка
Пины зависимостей без верхней границы (`mcp>=1.9.1`) позволяют CI молча
подтянуть мажорную версию с breaking changes или новыми уязвимостями при
следующей пересборке — стоит комбинировать SCA-скан с осознанным
верхним пином (`mcp>=1.9.1,<2.0.0`) для критичных зависимостей.
