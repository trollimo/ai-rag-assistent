# Access Control и аутентификация

## Broken Access Control — самая частая уязвимость на практике
Не экзотика вроде инъекций, а банальное: эндпоинт проверяет, что пользователь
залогинен, но не проверяет, что он имеет право именно на ЭТОТ ресурс.

```python
# Уязвимо: любой залогиненный юзер может подставить чужой id
@app.get("/orders/{order_id}")
def get_order(order_id: int, user: User = Depends(current_user)):
    return db.get_order(order_id)

# Правильно: проверка владения ресурсом
@app.get("/orders/{order_id}")
def get_order(order_id: int, user: User = Depends(current_user)):
    order = db.get_order(order_id)
    if order.user_id != user.id and not user.is_admin:
        raise HTTPException(403)
    return order
```
Это называется **IDOR** (Insecure Direct Object Reference) — самый частый
подвид Broken Access Control. Проверять на каждом эндпоинте, принимающем ID
в пути или теле запроса.

## Аутентификация: пароли
- хешировать через bcrypt/argon2 (с солью и адаптивной сложностью), никогда
  не MD5/SHA1/SHA256 напрямую — они слишком быстрые, брутфорсятся;
- rate-limit на попытки логина (например, 5 попыток / 15 минут на IP+логин);
- не раскрывать в ответе, что именно неверно — «неверный логин или пароль»,
  а не «пользователь не найден» (иначе можно перебором узнавать существующие
  аккаунты).

## Сессии и токены
```
# Плохо — сессионная кука без флагов
Set-Cookie: session=abc123

# Хорошо
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Strict
```
- `HttpOnly` — недоступна для JS (защита от кражи через XSS);
- `Secure` — только по HTTPS;
- `SameSite=Strict/Lax` — защита от CSRF.

## JWT — частые ошибки
- проверять `alg` в заголовке токена: атака `alg: none` или подмена
  RS256→HS256 (сервер начинает проверять подпись публичным ключом как
  секретом HMAC) — библиотека должна быть настроена на конкретный ожидаемый
  алгоритм, не брать `alg` из самого токена;
- короткий TTL для access-токена (минуты-часы) + отдельный refresh-токен с
  возможностью отзыва — bare JWT без сессии на сервере невозможно
  инвалидировать досрочно (например, при компрометации).

## Многофакторная аутентификация (MFA)
Обязательна для админ-панелей и любых действий с повышенными привилегиями
(смена email/пароля, выдача прав, финансовые операции) — даже если основной
логин без MFA.

## Чеклист для code review
- новый эндпоинт с `{id}` в пути — есть ли проверка владения ресурсом?
- новый admin-функционал — защищён ли ролевой проверкой, а не просто
  «залогинен»?
- токены/пароли — не логируются ли случайно (`logger.info(f"login: {password}")`)?
