# Режимы работы и все ключи конфигурации

Один образ умеет работать в нескольких конфигурациях. Здесь собрано **всё**,
чем это переключается, и что при этом меняется.

Общий принцип: **по умолчанию включён минимальный вариант** — один контейнер
ассистента (плюс LLM), никаких дополнительных сервисов. Всё остальное
включается явно и требует своего профиля в `docker-compose.yml`.

```powershell
docker compose up -d                              # базовый: ассистент + LLM
docker compose --profile chroma up -d             # + Chroma сервером
docker compose --profile feedback up -d           # + обратная связь
docker compose --profile chroma --profile feedback up -d   # всё сразу
```

---

## 1. Подключение к LLM

Где: переменные окружения сервиса `assistant`.

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `LLM_BASE_URL` | `http://localhost:9080` | Любой OpenAI-совместимый эндпоинт |
| `LLM_MODEL_NAME` | `qwen2.5` | Имя модели |
| `LLM_API_KEY` | пусто | Токен, если эндпоинт его требует |

Локальный `llama-server` из сервиса `llm` или корпоративная модель — форма API
одна и та же. Если используете внешнюю модель, сервис `llm` можно не поднимать
вовсе: `docker compose up -d assistant`.

Устаревшие синонимы `LLAMA_HOST` / `LLAMA_MODEL` ещё читаются, но новые деплои
должны использовать `LLM_*`.

## 2. Хранилище векторов (Chroma)

Где: `CHROMA_MODE` у ассистента и `storage.mode` в
`rag-generation/config/rag-sources.yaml`. **Оба должны указывать на одно и то же
хранилище.**

| Режим | Что делает | Когда нужен |
|---|---|---|
| `file` (по умолчанию) | Индекс открывается напрямую из тома | Обычная работа, локальная разработка без Docker |
| `server` | Отдельный контейнер `chroma`, оба процесса — его клиенты | Когда нужна переиндексация **без остановки ассистента** |

### Ассистент

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `CHROMA_MODE` | `file` | `file` или `server` |
| `CHROMA_HOST` | `chroma` | Имя сервиса внутри compose-сети |
| `CHROMA_PORT` | `8000` | Порт внутри контейнера |
| `RAG_DB_PATH` | `/data/chroma_db` | Путь к индексу в режиме `file` |

### Генератор (`rag-sources.yaml` → `storage`)

| Ключ | По умолчанию | Переменная окружения |
|---|---|---|
| `mode` | `file` | `RAG_CHROMA_MODE` |
| `host` | `localhost` | `RAG_CHROMA_HOST` |
| `port` | `8001` | `RAG_CHROMA_PORT` |
| `path` | `./output/chroma_db` | — |

### Как переключиться на серверный режим

```powershell
cd assistant-container
$env:CHROMA_MODE = "server"
docker compose --profile chroma up -d
```

Затем генератор — в том же режиме:

```powershell
cd ..\rag-generation
$env:RAG_CHROMA_MODE = "server"
$env:RAG_CHROMA_PORT = "8001"
docker compose run --rm generator
```

Порт `8001` — это проброс `chroma` на хост. Он нужен потому, что генератор
живёт в **другом compose-проекте** со своей сетью и по имени `chroma` сервис не
увидит. Альтернатива — общая внешняя сеть, но это лишний шаг при запуске.

### Что даёт и чего не даёт серверный режим

**Даёт:** запись в индекс при работающем ассистенте. Это снимает цикл
«остановить → подменить папку → поднять (~2 минуты на перезагрузку модели
эмбеддингов)» и делает возможной автоматическую переиндексацию по вебхуку.

**Не даёт:** ускорения. Эмбеддинги считаются на стороне клиента в обоих
режимах, а это 99% времени индексации. Поиск в серверном режиме даже чуть
медленнее — добавляется сетевой хоп (единицы мс на фоне 1-2 с эмбеддинга).

### ⚠️ Новые чанки не ищутся до перезапуска `chroma`

**Проверено на 1.5.9, и это главное ограничение режима.** Записанные при живом
ассистенте чанки попадают в хранилище, но **не появляются в векторном поиске**,
пока контейнер `chroma` не перезапустят:

| Проверка | До рестарта `chroma` | После |
|---|---|---|
| `count` коллекции | 235 (новые видны) | 235 |
| `/topics` | новый документ в списке | в списке |
| Поиск по новому документу | **не находит** | находит, дистанция 208 |

Ждать бесполезно — проверял с интервалами до 90 секунд, само не рассасывается.
Похоже, сервер не подхватывает дозаписанные векторы в HNSW-индекс на лету.

Поэтому реальный сценарий выглядит так:

```powershell
# ассистента НЕ трогаем, он продолжает отвечать
docker compose run --rm generator          # в rag-generation, mode=server
docker restart rag-chroma                  # ~10-25 с, поиск недоступен
```

**Что это меняет.** Полностью бесшовной переиндексации не получается, но выигрыш
остаётся: перезапускается `chroma` (~10-25 с) вместо ассистента (~2 минуты на
перезагрузку модели эмбеддингов), и не нужна возня с подменой папок. Для
вебхука это по-прежнему пригодно — окно недоступности поиска короткое и
предсказуемое, — но обещать «совсем без простоя» нельзя.

**Полный ребилд** (смена модели или чанкинга) сначала удаляет коллекцию:
ассистент не упадёт, но будет отвечать «не нашёл» по полупустой базе. Это хуже
честного простоя, потому что незаметно. Такие ребилды делайте в окно.

Миграция данных не нужна: формат на диске одинаковый, сервер поднимается
поверх существующей папки `output/chroma_db` — проверено, 233 чанка
подхватились как есть.

## 3. Поиск и промпты

Где: `assistant-container/backend/config/mcp-tools.yaml`. Файл вшит в образ;
чтобы править без пересборки, раскомментируйте его bind-mount в
`docker-compose.yml`.

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `search.default_top_k` | `5` | Сколько чанков возвращать |
| `search.max_distance` | `300` | Отсекать результаты дальше этой дистанции. **Не применяется к топ-1** — короткие keyword-запросы дают дистанцию заметно выше, а топ-1 почти всегда всё равно верный. `null` — не отсекать |
| `search.normalize_query` | `true` | Доп. вызов LLM, разворачивающий сленг («кубер» → «Kubernetes») перед эмбеддингом. Стоит +1 обращение к модели на вопрос |
| `topics.default_top_k` | `100` | Сколько тем отдавать |
| `topics.max_topics` | `500` | Потолок тем в одном ответе |
| `llm.max_tokens` | `4096` | Потолок длины ответа |

`normalize_query` — мастер-выключатель: если он `false`, переключатель в
настройках UI включить нормализацию **не может**, только выключить при
включённом мастере.

## 4. Эмбеддинги

Где: переменные окружения обоих контейнеров.

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `RAG_EMBED_BATCH_SIZE` | 256 (генератор: 32) | Размер ONNX-батча. У генератора занижен: батч в 224 чанка укладывал контейнер по OOM в лимите памяти Docker Desktop |
| `RAG_EMBED_THREADS` | все ядра | Потоки ONNXRuntime |
| `RAG_EMBED_PARALLEL` | не задано | Параллелизм fastembed |
| `RAG_EMBED_E5_PREFIXES` | выкл | Префиксы `query:`/`passage:`, которых требует e5. На текущем корпусе замерялись **чуть хуже**, поэтому выключены |

`RAG_EMBED_E5_PREFIXES` меняет векторы документов — **переключение требует
полной переиндексации**, иначе запросы и документы окажутся в разных
пространствах.

## 5. Скиллы

| Ключ | Где | По умолчанию | Смысл |
|---|---|---|---|
| `RAG_SKILLS_PATH` | env | `/data/skills` | Папка с архивами и `index.json` |
| `PUBLIC_BASE_URL` | env | `http://localhost:8000` | Адрес, попадающий в `download_url` для MCP-агентов. Должен быть виден **снаружи** контейнера |
| `skills.install_hint` | yaml | путь OpenCode | Шаблон команд установки |
| `type: skills` | `rag-sources.yaml` | — | Помечает источник как папку со скиллами |
| `archive.exclude` | `rag-sources.yaml` | `.git`, `.idea`, `node_modules` | Что не класть в архив |
| `archive.max_size_mb` | `rag-sources.yaml` | `25` | Потолок размера архива |

`PUBLIC_BASE_URL` — частая ошибка: `localhost` в нём означает машину
**агента**, а не сервер. Если ассистент не на машине разработчика, адрес надо
поменять, иначе скачивание архива у агента не сработает.

## 6. Обратная связь

Где: секция `feedback` в `mcp-tools.yaml` плюс env. Подробности —
[`feedback-architecture.md`](feedback-architecture.md).

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `feedback.enabled` | `false` | **Мастер-выключатель.** Выкл — БД не трогается вообще, кнопки реакций и вкладка «Запросы» скрыты, поведение как до появления модуля |
| `feedback.log_questions` | `true` | Писать все взаимодействия, а не только оценённые. Выкл — на диск попадает только то, по чему нажали кнопку |
| `feedback.redact` | `true` | Чистка секретов до записи. Выключать не стоит |
| `feedback.showcase` | `true` | Публичная вкладка «Запросы» |
| `feedback.publish_threshold` | `2` | Сколько **разных** людей должны спросить, чтобы тема стала публичной |
| `feedback.cluster_interval_minutes` | `10` | Как часто группировать непокрытые вопросы в темы |
| `feedback.cluster_max_distance` | `180` | Порог «это одна тема» |
| `FEEDBACK_DB_URL` | env | Строка подключения к Postgres |
| `ADMIN_TOKEN` | env, пусто | Токен для `/admin/*`. **Пустой выключает админ-API целиком**, а не открывает его всем |

## 7. Прочее

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `LOG_LEVEL` | `INFO` | `DEBUG` печатает контекст RAG и промпты целиком |
| `MCP_SERVER_URL` | `http://localhost:9081/mcp` | Адрес MCP для подсказок в UI |
| `NEXT_PUBLIC_FASTAPI_URL` | `http://localhost:8000` | Адрес API **со стороны браузера** — вшивается в бандл при сборке |

`NEXT_PUBLIC_FASTAPI_URL` подставляется во фронтенд на этапе `npm run build`,
поэтому его смена требует пересборки бандла, а не только перезапуска.

## Матрица: что запускать под какую задачу

| Задача | Команда | Сервисы |
|---|---|---|
| Обычная работа | `docker compose up -d` | assistant, llm |
| Внешняя корпоративная модель | `docker compose up -d assistant` | assistant |
| Переиндексация без простоя | `CHROMA_MODE=server docker compose --profile chroma up -d` | + chroma |
| Сбор обратной связи | `docker compose --profile feedback up -d` + `feedback.enabled: true` | + feedback-db |
| Всё вместе | оба профиля | 4 сервиса |
